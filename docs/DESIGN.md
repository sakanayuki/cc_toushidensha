# 投資電車（仮） 設計仕様書

日本各地の鉄道路線と、普通／急行／特急の停車駅を忠実に再現した、旅行型の資産形成ボードゲーム。
GitHub Actions 経由で GitHub Pages に公開する静的 Web アプリ。

- 公開URL: `https://sakanayuki.github.io/cc_toushidensha/`
- リポジトリ: `sakanayuki/cc_toushidensha`

---

## 1. ゲーム概要

プレイヤーは6つの開始駅から1つを選び、鉄道で日本各地を旅しながら各駅の産業へ投資する。
規定ターン（既定5ターン）終了後、その回に抽選された**5つのトロフィー**について
それぞれ No.1 のプレイヤーが受賞し、**最も多くトロフィーを獲得した人が優勝**。

- プレイ人数: 1〜4人（人間とCPUを自由に混成）
- 対戦形式: 同一端末の回し持ち（ホットシート）+ CPU
- 1ゲームの所要時間: 5〜10分程度
- 主ターゲット画面: スマートフォン縦向き

### コアループ

```
[ゲーム開始]
   ↓
 トロフィー5枚を抽選・公開     ← 全員に見える状態で開始駅を選ぶ
   ↓
 各プレイヤーが開始駅を選択     ← 重複可
   ↓
 ┌─ ターン開始 ────────────────────┐
 │  1. 種別を選ぶ（普通 / 急行 / 特急）  ← 現在地に停車する種別のみ
 │  2. サイコロを振る（1〜6）
 │  3. ちょうどN駅先の到達可能駅から1つ選ぶ
 │  4. 到着駅の産業から1つ選んで投資
 └──────────────────────────────┘
   ↓ （規定ターン数ぶん繰り返し）
 トロフィー判定 → 優勝者決定
```

## 2. ゲームルール

### 2.1 移動

**手順は「種別 → サイコロ → 到達駅」の順に確定する。**

1. **種別選択（サイコロを振る前）**
   - 普通 / 急行 / 特急 / 新幹線 の4種別。**現在地に停車する種別のみ**選択できる。
   - 実際の列車名が「区間快速」「通勤特急」などであっても、急行・特急に名称統一する。
   - 新幹線が停まる駅はごく限られる（フェーズ1では152駅中5駅）ため、
     **在来線の3種別は常に並べ、新幹線は乗れるときだけ4つ目として下に現れる**（→ 9.1）。

2. **サイコロ**
   - 1個、出目 1〜6。

3. **到達駅の選択**
   - 選んだ種別の停車駅グラフ上で、**ちょうど N 駅先**に到達できる駅がすべて地図上にハイライトされ、
     その中から1つを選んで移動する。
   - **乗り換えの概念は存在しない。** 路線の終点に達しても、その駅から先に線路が続いていれば
     そのまま進む（内部的には駅ノードを共有するグラフを辿るだけ）。
   - **逆走禁止**: 1回の移動の経路内で同じ駅を二度通ることはできない。
     ただしこの制約は**1回の移動内のみ**に適用され、ターンが変われば来た方向へ引き返してよい
     （これが無いと盲腸線で詰む）。
   - **行き止まり**: ちょうど N 駅先に到達可能な駅が1つも無い場合は、
     **到達できる最遠の駅で停車する**。候補が複数あればその中から選択する。

4. **投資**
   - 到着駅（停車駅）でのみ投資できる。**通過駅では投資できない。**
   - 停車につき**1つだけ**取得する。所持金の概念は無く、取得は無料。
   - 同じ産業を**他のプレイヤーも**取得できる（独占なし）。
   - ただし**同一プレイヤーが同じ産業を重複保有することはできない**。
     その駅の別の産業を選ぶ。全て保有済みならその回は投資なし。

### 2.2 交通費

交通費に支払い能力の制約は無く、**トロフィー判定用のカウンタ**としてのみ機能する。

```
交通費 = 移動した区間の距離(km) の合計 × 種別係数
```

| 種別 | 係数 |
|---|---|
| 普通 | 1.0 |
| 急行 | 1.3 |
| 特急 | 2.2 |
| 新幹線 | 3.0 |

### 2.3 ターン

- 既定 5 ターン。ゲーム開始画面で **3 / 5 / 8 / 10** から選択可能。
- ターン順はゲーム開始時にランダムに決定し、以降固定。
- 全プレイヤーが同じターン数を消化する。

## 3. トロフィー

### 3.1 トロフィー一覧（9種）

| ID | 名称 | 判定 | 方向 |
|---|---|---|---|
| `scale_total` | 産業規模の合計 | 保有産業の規模の総和 | 最大 |
| `max_profit_rate` | 最大利益率 | 保有産業の利益率の最大値 | 最大 |
| `best3_count` | 全国ベスト3 | 全国区カテゴリでトップ3の産業の保有数 | 最大 |
| `sector1_count` | 第一次産業 ※排他 | 第一次産業の保有数 | 最大 |
| `sector2_count` | 第二次産業 ※排他 | 第二次産業の保有数 | 最大 |
| `sector3_count` | 第三次産業 ※排他 | 第三次産業の保有数 | 最大 |
| `distance` | 旅の距離 | 開始駅と最終地点の直線距離 | 最大 |
| `fare_min` | 節約王 | 交通費の合計 | **最小** |
| `rural` | 地方創生 | 保有産業の規模の**最小値** | **最小** |

### 3.2 抽選ルール

1. `sector1_count` / `sector2_count` / `sector3_count` の**3枚は排他**。この中から**1枚だけ**をランダムに選ぶ。
2. 選ばれた分類系1枚 + 非分類系6枚 = **7枚のプール**を作る。
3. プールから**5枚**をランダムに抽選する。
4. 抽選結果は**開始駅を選ぶ前に公開**され、以降ゲーム中ずっと表示され続ける。

### 3.3 同点処理

**必ず1人だけが受賞する。** 同点の場合は以下の順で決着させる。

1. **同点対象の産業規模合計**が大きい方
   （例: 第一次産業2個同士なら、その2個の規模の合計で比較）
2. **知名度点の合計**が高い方
3. **手番が後のプレイヤー**（先手は他人の盤面を見ずに選ぶ不利を負うため、その補償）

### 3.4 優勝判定

1. 獲得トロフィー枚数
2. 知名度点の合計
3. 投資した産業規模の合計
4. それも同じなら**同率優勝**

## 4. データ設計

データは `src/data/` 配下の TypeScript モジュールとして、ロジックから分離して持つ。
JSON ではなく TypeScript にしているのは、駅IDの参照切れや分類の取りこぼしを
コンパイル時に検出するため。修正のしやすさは JSON と変わらない。

### 4.1 型定義

```ts
type StationId  = string;  // 例: "yosan-matsuyama"
type LineId     = string;  // 例: "yosan"
type IndustryId = string;  // 例: "matsuyama-tourism"
type CategoryId = string;  // 例: "mikan"

type TrainType = 'local' | 'express' | 'ltd' | 'shinkansen';  // 普通 / 急行 / 特急 / 新幹線

interface Station {
  id: StationId;
  name: string;      // 表示名（例: "松山"）
  kana: string;      // 検索・ソート用
  pref: string;      // 都道府県（例: "愛媛県"）
  lat: number;       // 緯度
  lon: number;       // 経度
  industries: IndustryId[];  // 1〜3個。最低1個は必須
}

interface Line {
  id: LineId;
  name: string;              // 例: "予讃線"
  operator: string;          // 例: "JR四国"
  /**
   * 新幹線の路線か。新幹線には在来線の普通・急行・特急が走らないので、
   * 「普通列車は全駅に停車する」といった在来線の前提から外して扱う。
   */
  isShinkansen?: boolean;
  /**
   * 環状線か。true のとき、stations の末尾と先頭も隣接しているものとして繋ぐ。
   */
  isLoop?: boolean;
  /** 起点→終点の順に並べた全駅。隣接関係の定義元。 */
  stations: StationId[];
  /**
   * 種別ごとの停車駅。stations の部分集合であり、同じ順序を保つ。
   * local は原則 stations と一致する。
   * 同一路線に複数の優等列車が走る場合は「どれか1本でも停まる駅」の和集合とする
   *（例: 予讃線の ltd は しおかぜ・いしづち・宇和海 の停車駅の和集合）。
   */
  stops: Record<TrainType, StationId[]>;
  /**
   * 隣接駅間の営業キロ。省略時は緯度経度からの大円距離 × 1.15 で近似する。
   * 長さは stations.length - 1。
   */
  distancesKm?: number[];
}

interface Industry {
  id: IndustryId;
  name: string;          // 例: "みかん"
  sector: 1 | 2 | 3;     // 第一次 / 第二次 / 第三次
  scale: number;         // 産業規模（実態準拠。利益率と相関を付けない）
  profitRate: number;    // 利益率 %（実態準拠）
  /** 全国区産業のみ設定。全国的に有名な産業だけが知名度点を持つ。 */
  fame?: {
    categoryId: CategoryId;
    rank: 1 | 2 | 3 | number;  // カテゴリ内の全国順位
    score: number;             // 知名度点
  };
}

interface FameCategory {
  id: CategoryId;
  name: string;              // 例: "みかん"
  /**
   * 全国1〜3位の産地名。UI の豆知識表示に使う。
   * 「全国ベスト3」の判定そのものは Industry.fame.rank <= 3 で行う。
   * トップ3の産地は収録範囲外にあることが多いため（例: お茶の1〜3位は
   * フェーズ1の収録範囲に1つも無い）、産業IDではなく表示用の文字列で持つ。
   */
  top3Labels: [string, string, string];
}
```

### 4.2 移動グラフの構築

種別ごとに**駅ノードのグラフ**を構築する。

- ノード = 駅（`StationId`）
- エッジ = 同一路線の `stops[type]` 上で**連続する2駅**
- エッジの重み = その2駅間の距離（間の通過駅を含めた営業キロの合計）

**路線をまたぐ接続は自動的に成立する。** 複数路線が同じ駅を通る場合、その駅は同一ノードなので
グラフとして既に繋がっており、「乗り換え」という処理は一切要らない。
これがルール 2.1 の「乗り換えの概念は考慮しない」の実装そのものになる。

到達可能駅の探索は、このグラフ上で**訪問済みノードを許さない深さ優先探索**を
深さちょうど N まで行い、終端ノードの集合を返す。

### 4.3 データ整合性の CI 検証（Vitest）

デプロイ前に以下を自動チェックし、壊れたデータの公開を防ぐ。

- 全 `Line.stations` の駅が駅マスタに存在する
- 全 `Line.stops[type]` が `Line.stations` の部分集合であり、順序も保たれている
- `local` グラフ上で全駅が連結している（到達不能な孤立駅が無い）
- 新幹線路線には在来線の種別が走っていない
- 新幹線の駅がすべて在来線にも接続している（在来線と繋がらない新幹線単独駅を
  入れると、普通列車のグラフから孤立してしまう）
- 全駅が最低1つの産業を持つ
- 全 `Industry.id` がユニークで、どこかの駅から参照されている
- 全 `Industry.fame` の参照先カテゴリが存在し、同一カテゴリ内で順位が重複しない
- 全国ベスト3の産業が全体の 1〜4 割に収まる（少なすぎると死に札、多すぎると同点だらけになる）
- 第一次・第二次・第三次のいずれもが十分な数ある
- `distancesKm` が指定されている場合、長さが `stations.length - 1` である
- 6つの開始駅が全て存在し、`local` グラフ上で相互に到達可能である

## 5. CPU（PvE）

本作は妨害要素が無く（産業は共有可）、相手の手を読む必要が無い。
したがって CPU は**自分の盤面の最適化のみ**を行う**貪欲法**で十分に強い。

### 評価関数

抽選された5枚のトロフィーそれぞれについて「この手を選んだ場合に自分が首位になれるか」を評価し、
期待獲得枚数が最大になる手を選ぶ。競合の少ないトロフィー（他プレイヤーとの差が大きい）を優先する。

### 難易度

単一の貪欲エンジンに**ランダム手の混入率**を変えるだけで3段階を作る。

| 難易度 | 挙動 |
|---|---|
| やさしい | 60% の確率でランダムな手を選ぶ |
| ふつう | 25% の確率でランダム。トロフィーは1〜2枚だけ意識する |
| つよい | 常に貪欲最適。全5枚を評価する |

難易度は CPU ごとに個別設定できる。

## 6. UI

デザインシステムは **Material 3 Expressive** に統一する。

色は `scripts/build-theme.ts` が Material 公式の material-color-utilities を使って
ソースカラーから生成し、`src/ui/theme.css` に書き出す。手で色を並べるのではなく
アルゴリズムに任せることで、コントラスト比と色相の調和が M3 の仕様どおりになる。
スキームは Expressive バリアント（`SchemeExpressive`）で、
彩度が高く secondary / tertiary が primary から大きく離れた色相になる。

| ファイル | 内容 |
|---|---|
| `src/ui/theme.css` | 色ロール（生成物・直接編集しない） |
| `src/ui/tokens.css` | タイポスケール・シェイプ・モーション・エレベーション |
| `src/ui/components.css` | ボタン・カード・リスト・チップ等の M3 部品 |
| `src/ui/app.css` | ゲーム固有のレイアウト |

Expressive の性格は主に3点で出す。

- **シェイプが大きい**：ボタンは `corner-full`、カードは `corner-extra-large`
- **押すと角丸が縮む形の変化**（shape morph）と、わずかに行き過ぎて戻るスプリング
- **container 系の色を面で使う**：彩度の高さをそのまま見せる

**ライトを既定とする。** 地図と路線を見るゲームなので、明るい地の上のほうが
線と駅を追いやすい。端末が `prefers-color-scheme: dark` でもライトのまま表示し、
`color-scheme: light` を指定してブラウザ側の UI もライトに固定する。
ダークスキームも生成してあり、`<html data-theme="dark">` を明示したときだけ有効になる。

### 6.1 レイアウト（スマホ縦優先）

```
┌─────────────────────────┐
│ トロフィー5枚 × 現在の首位者     │ ← 常時表示。タップで全員の順位を展開
│ （コンパクトグリッド 2列×3行）    │
├─────────────────────────┤
│                         │
│  日本地図＋路線図（SVG）      │ ← 海岸線の上に路線を重ねる
│  陸地・県境 → 路線 → 駅 →   │   ズーム／パン対応
│  ハイライト → コマ の順に重ねる │   現在地周辺は自動的に拡大
│                         │
├─────────────────────────┤
│  操作パネル / 自分の保有産業     │
└─────────────────────────┘
```

PC・タブレットでは地図とパネルを左右に並べる程度の簡易レスポンシブに留める。

### 6.1.1 地図レイヤー

投影は **Web メルカトル**（経度1度 = 1000 単位）。駅も海岸線も同じ関数で変換するので、
路線と陸地が実際の位置関係どおりに重なる。緯度によって縦が引き伸ばされるのが正しい姿で、
全国に拡張しても形が崩れない。

- **元データ**: 地球地図日本（国土地理院）由来の都道府県ポリゴン
- **利用条件**: 出典の明記。README と地図上のクレジットに表示している
- **簡略化**: `scripts/build-japan-geojson.py` が 13MB / 8万点を 435KB / 2.3万点に落とす
  （極小の島を除去 → Douglas-Peucker で頂点を間引き → 座標を4桁に丸め）
- **配信**: `?url` で読み込むので JS バンドルには入らず、別ファイルとして非同期に取得する。
  地図が無くても路線図だけでゲームは成立する

陸・海・県境の色は M3 の色ロールから引くが、「陸が明るく海が沈んで見える」関係の作り方は
ライトとダークで異なるため、`--map-sea` / `--map-land` / `--map-border` という
地図用のセマンティックな名前に束ねてテーマごとに割り当てる。
既定のライトでは海が tertiary-container の淡い青、陸が最も明るい面になる。

地図を収めるときは viewBox を画面と同じ縦横比に広げる。SVG は viewBox 全体が収まるよう
縮小するため、比率を合わせずに寄せると短い辺に合わせて縮み、
長い辺の端（＝到達可能駅）が画面の外に出てしまう。

**出目が確定して行き先の候補が出たら、手動でパン・ズームした後でも追従を再開する。**
候補がすべて画面に入っていないと、どこへ行けるのかを見て選べないため。
新幹線のように候補が100km以上離れる場合も、その全体が入る倍率まで自動的に引く。

### 6.2 トロフィー常時表示

- 各セルに「トロフィー名 + 現在の首位者の色と名前」を表示
- タップすると全員の順位・現在値・**逆転に必要な差**を展開
- 首位が入れ替わった瞬間はハイライトして通知する

### 6.2.1 種別の選択

在来線の普通・急行・特急は常に3つ並べ、その駅に停車しないものは押せない状態で見せる。
**新幹線だけは、その駅に停車するときにのみ4つ目として現れる。**
停まる駅が全体の3%しかないため常設すると無駄な枠になり、
逆に現れたときの「ここは新幹線に乗れる駅だ」という気付きが強くなる。

### 6.3 演出

- **コマの駅ごと移動アニメーション（必須機能）**
  通過駅を高速で流し、停車駅で止まる。これにより「なぜ特急なら3駅で名古屋なのか」が視覚的に伝わり、
  停車駅を忠実に再現した価値がプレイヤーに届く。
- サイコロの回転アニメーション
- 投資時のカード表示
- 結果発表はトロフィーを1枚ずつ順に開示
- 効果音は最小限（サイコロ・投資確定・トロフィー獲得）。BGM なし
- すべて CSS / SVG アニメーションで実装し、外部アセットは使わない

### 6.4 その他

- 言語: 日本語のみ
- `localStorage` へ毎手オートセーブし、リロード・中断から復帰できる

| ホスティング | GitHub Pages |

### 7.1 ディレクトリ構成

```
scripts/
  build-theme.ts         # M3 の配色を生成して src/ui/theme.css に出力
  build-japan-geojson.py # 日本地図を配信できるサイズまで簡略化
src/
  data/            # 駅・路線・産業のデータと、日本地図 GeoJSON
  engine/          # ルールエンジン（純粋関数・UI 非依存）
    graph.ts       #   種別ごとの移動グラフ構築、到達可能駅探索
    trophy.ts      #   トロフィー判定・同点処理・優勝判定
    fare.ts        #   交通費・距離計算
    cpu.ts         #   CPU 思考
    state.ts       #   ゲーム状態と遷移
  ui/              # React コンポーネント
  __tests__/       # ルールエンジンのユニットテスト＋データ整合性検証
.github/workflows/
  deploy.yml       # main への push で テスト → ビルド → Pages へデプロイ
```

**ルールエンジンは UI から完全に独立した純粋関数として実装する。**
これによりユニットテストが可能になり、将来オンライン対戦を追加する際も再利用できる。

### 7.2 デプロイ

`main` ブランチへの push をトリガーに、GitHub Actions で以下を実行する。

1. 依存インストール
2. **Vitest 実行**（ルールエンジンのテスト + データ整合性検証）
3. Vite ビルド
4. `actions/deploy-pages` で GitHub Pages へ公開

テストが落ちた場合はデプロイしない。

収録した路線については**駅を間引かず全駅を収録している**。
駅を間引くと「普通で4駅／急行で1駅」というコアな対比が歪み、
検証したいメカニクスそのものが壊れるため。

**開始駅**: 松山・高松・徳島・岡山・広島・三宮・大阪の7つ。
仕様上の6駅（札幌・東京・名古屋・大阪・松山・博多）のうち収録範囲に入るのは松山だけなので、
範囲内の主要ターミナルで代替している。フェーズ2で本来の6駅に差し替える。

四国を選んだ理由:

- **在来線特急が全主要路線に走っている**（しおかぜ・いしづち・宇和海・南風・しまんと・うずしお・剣山）ため、
  普通／急行／特急の3択というコア機能を実地で検証できる
- 駅数が最小でデータ作成が早い
- 開始駅「松山」を最初から含められる
- 島として閉じているため路線網の整合性を検証しやすい
- **予土線という行き止まり路線**があるので、行き止まり処理も実地検証できる
- 高松・多度津・伊予市などに分岐があり、「到達可能駅を選ぶ」体験も検証できる

**このフェーズで全機能を実装し、GitHub Pages への公開まで完了させる。**
実際に遊ぶことで以下を確定させる。

- ターン数（5 が適切か）
- トロフィーのバランス
- データスキーマの過不足
- 停車駅データの精度

## 9. 既知の課題・留意事項

### 9.1 新幹線の扱い

新幹線は**第4の独立した種別**として収録する。当初は「特急に統合すると飛距離が壊れる」
という理由で収録を見送っていたが、統合せず独立させれば問題は起きない。

飛距離が支配的にならないよう、次の3点で抑えている。

1. **乗れる駅が極端に少ない。** フェーズ1では152駅中5駅（3%）しか新幹線が停まらない。
   在来線と同じく「その駅に停車する種別しか選べない」ので、新幹線に乗るには
   まず新幹線停車駅まで在来線で辿り着く必要がある。
2. **交通費係数が最も高い（3.0）。** 節約王トロフィーと正面から対立する。
3. **UI でも常設しない。** 在来線の3種別は常に並べ、新幹線は乗れるときだけ
   4つ目として下に現れる。「たまたま新幹線駅にいる」ことが分かる作りにしてある。

山陽本線（岡山〜広島）に定期の在来線特急が走っていないことが、この設計と噛み合っている。
この区間を速く移動する手段は新幹線だけで、しかも停まる駅は限られる。

### 9.2 全国拡張時の留意点

東海道本線には定期の在来線特急が走っていないため、**東京〜大阪を在来線で速く移動する手段は無い**。
新幹線を収録したことでこの区間は繋がるが、裏を返すと
**東京・名古屋・大阪の間は新幹線がほぼ唯一の選択肢**になる。
新幹線停車駅の密度がその区間だけ高くなりすぎないか、フェーズ2で確認する。

### 9.3 停車駅データの出所と精度

駅の位置や路線の接続には公開データ（国土数値情報など）があるが、
**「この特急がどの駅に停まるか」を網羅した機械可読なオープンデータは実質存在しない。**
時刻表由来の情報であり、ダイヤ改正のたびに変わる。

したがってこの部分は生成データであり、**一定の誤りが混入する前提**で扱う。
「忠実に再現」という本作の核心部分なので、データは JSON で外出しして修正を容易にし、
レビューによって精度を上げていく方針とする。

### 9.4 バランス設計上の既知のトレードオフ

産業の規模と利益率に人為的な相関を付けない（実態準拠）ため、
**規模も利益率も高い「当たり駅」**が存在する。そこを踏んだプレイヤーが複数トロフィーを
まとめ取りする展開が起こり得る。これは「トロフィー5枚のランダム抽選」と
「5投資しかできない制約」によって緩和されることを期待するが、
フェーズ1のプレイテストで検証する。

### 9.5 停車パターンの集約による副作用

同一路線に複数の優等列車が走る場合、停車駅を「どれか1本でも停まる駅」の和集合に集約している。
このため、複数系統が分岐する駅では**実在しない停車パターンが合成されることがある**。
またマリンライナーは実際には宇多津駅を短絡線で通過して坂出へ向かうが、
路線グラフの接続を保つため宇多津を停車駅として扱っている。

系統ごとに分けて保持すれば忠実度は上がるが、データ量とルールの複雑さが増すため、
フェーズ1では集約方式を採る。
